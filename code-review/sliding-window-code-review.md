# 代码审查场景：滑动窗口 + 字段截取策略

## 策略简介

针对代码审查（Code Review）场景的优化策略组合。通过滑动窗口保持上下文聚焦于最近的代码讨论，配合字段截取只保留关键代码和结论，大幅减少冗余 Token 消耗，同时保证审查质量。

## 适用场景

✅ **什么时候用这个策略：**

- 对单个文件或模块进行深度 Code Review
- 逐段讨论代码，每轮对话聚焦于一个具体问题
- 对话中包含大量代码输出，Token 消耗高
- 需要模型专注于当前正在审查的代码段，而不是整段对话的所有内容

❌ **什么时候不建议用：**

- 需要跨文件对比审查（建议用首尾保留策略）
- 审查过程中涉及大量架构设计讨论（建议切换全量模式）

## 策略配置

### 主策略：滑动窗口 (slidingWindow)

```json
{
  "strategy": "slidingWindow",
  "windowSize": 10,
  "includeSystemPrompt": true
}
```

**参数说明：**
- `windowSize: 10` — 保留最近 10 条消息。代码审查的有效信息通常集中在最近几轮
- `includeSystemPrompt: true` — 始终包含系统提示（审查标准、角色设定等）

### 辅助策略：字段截取 (fieldCut)

```json
{
  "strategy": "fieldCut",
  "fieldFilters": {
    "assistant": ["code", "conclusion", "issues"],
    "user": ["code", "question"]
  },
  "keepLatestFull": 2
}
```

**参数说明：**
- `fieldFilters` — 只保留代码、结论、问题等关键字段
- `keepLatestFull: 2` — 最近 2 条消息保留完整内容，确保当前讨论不丢失细节

## 使用技巧

### 1. 窗口大小怎么调？

| 审查类型 | 推荐窗口大小 | 原因 |
|---------|------------|------|
| 简单语法/风格审查 | 6-8 轮 | 每轮问题独立，不需要太多上下文 |
| 逻辑深度审查 | 10-12 轮 | 需要理解前后关联的逻辑 |
| 架构设计审查 | 15+ 轮 | 上下文依赖强，需要更多背景 |

### 2. 配合系统提示效果翻倍

在对话开头设置清晰的系统提示，因为系统提示始终保留在窗口内：

```
你是一位资深代码审查专家，负责审查以下代码：
- 重点关注：逻辑错误、性能问题、安全漏洞、边界情况
- 输出格式：先列问题，再给改进建议，最后附修改后的代码
- 每发现一个问题，用 [严重/中等/轻微] 标注级别
```

### 3. 什么时候切换策略

- **讨论到架构问题时** → 切换为「首尾保留」，头部保留架构背景
- **发现需要回退的方向时** → 切换为「手动截断」，隔离错误方向
- **最终总结时** → 切换为「全量上下文」，让模型看到完整审查过程

## 效果案例

### 用户案例：后端模块 Code Review

**背景：** 对一个 500 行的 Go 语言微服务模块进行代码审查，涉及错误处理、并发安全、性能优化三个维度。

**使用前：**
- 对话 32 轮，总 Token 消耗：约 12,400
- 中间模型有 3 次跑题（回到前面已经讨论过的问题）
- 平均响应时间：约 11 秒
- 因为上下文混乱，有 2 个问题需要重新描述

**使用滑动窗口+字段截取后：**
- 对话 28 轮（更少的重复纠正）
- 实际发送 Token：约 5,800（节省 53%）
- 模型全程聚焦，无明显跑题
- 平均响应时间：约 5 秒（提升 6 秒）
- 审查结论更清晰，问题分类更准确

**用户评价：**
> "以前 Code Review 聊到后面，AI 就开始东拉西扯。用了滑动窗口之后，每一轮回答都很精准，就像在跟一个专注度满分的同事 Review 一样。"
